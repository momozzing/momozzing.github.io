Worse Together: How Performance Breaks Down in Multi-User Multi-Agent Teams

[https://arxiv.org/abs/2610.00583](https://arxiv.org/abs/2610.00583)

독립 연구자 Sahan Paliskara, Stanford University의 Nattaput Namchittai, Anthropic의 Andrew Lampinen이 쓴 논문이다.
Paliskara와 Namchittai는 Anthropic Fellows Program에서 이 연구를 진행했다.
arXiv에 올라온 논문이다.
사용자마다 에이전트를 하나씩 두고, 예산이나 일정처럼 여러 사람이 같이 쓰는 자원을 맡겨 봤다.

![사용자와 에이전트, 공유 자원을 연결하는 네 가지 구성 (논문 Figure 1)](https://momozzing.github.io/assets/images/worse-together/fig1-four-formations-compare.png)

이 글의 그림과 표는 위에 링크한 Paliskara, Namchittai, Lampinen의 arXiv:2610.00583v1 PDF에서 해당 영역을 잘라 옮겼다. [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

## **1. Introduction**

여러 사람이 각자의 에이전트에게 일을 맡기면 같은 예산, 달력, 저장소에서 만날 수 있다.
한 사용자의 입장에서는 먼저 예약하거나 예산을 잡아 두는 게 합리적이다.
모두가 그렇게 움직이면 더 급한 일이 밀리고, 해 놓은 일이 마감까지 끝나지 않을 수 있다.

저자들은 각 사용자에게 에이전트를 붙인 팀과 한 에이전트가 모든 사용자를 맡는 구성을 비교했다.
사용자마다 요구가 다르지만, 어느 일을 양보할지 조정하면 전체 결과를 개선할 수 있는 상황을 만들었다.
어떤 행동이 실패와 함께 나타나는지 기록하고, 역할·지시·도구 제약을 바꿔 봤다.

## **2. Related Work**

이전 연구에는 하나의 목표를 여러 에이전트가 나누는 실험과, 공유 자원을 두고 협력하는 게임 실험이 있다.
GovSim(공유 자원을 고갈시키지 않고 이용하는지를 보는 시뮬레이션), CoopEval(사회적 딜레마에서 협력을 평가하는 벤치마크), DPBench(공유 자원에서 교착이 생기는 조건을 평가하는 벤치마크)가 후자에 속한다.
이 논문에서는 사용자별 요청이 있는 도구 환경을 만들고, 실제로 어떤 일이 끝났고 요청이 반영됐는지 점수를 매긴다.

## **3. Experimental Setup**

조정자(coordinator)는 에이전트 하나가 모든 사용자의 요청을 받는다.
무통신 팀(silent team)은 사용자마다 별도 컨텍스트를 가진 에이전트를 두고, 동료에게 직접 메시지를 보내는 기능을 뺀다.
메시지 팀(peer-to-peer team)은 같은 구성에서 동료와 소통할 수 있다.
공유 API 예산과 병합 대기열에는 한 사용자와 한 에이전트로 이루어진 solo 대조군도 뒀다.
공유 달력처럼 여러 에이전트가 읽고 쓰는 상태는 직접 메시지를 꺼도 남을 수 있다.

API 예산 25개, 병합 대기열 3개, 진료 예약 24개, 개인 비서 25개로 총 77개 시나리오다.
모델은 환경마다 최대 다섯 개를 썼다.
Claude Opus 5, Claude Sonnet 5, GPT-5.6-sol, GPT-5.6-terra, Qwen3.8-max다.
시나리오와 구성마다 기본 20회 실행했지만, 개인 비서는 모델별로 50회 또는 100회, 진료 예약의 무통신 팀은 5회였다.
환경별로 에이전트를 깨우는 순서와 시간이 흐르는 조건도 다르다.
95% 구간은 실험에 포함된 시나리오를 기준으로 계산했다.

아래 그림은 두 Claude 모델의 환경별 결과다.
API 예산과 병합 대기열은 실행 가능한 최적 계획 대비 가치, 진료 예약은 두 환자 조건을 함께 만족한 비율, 개인 비서는 특정 사용자 요청을 지킨 비율을 비교한다.

![두 Claude 모델이 네 환경에서 기록한 구성별 결과 (논문 Figure 2)](https://momozzing.github.io/assets/images/worse-together/fig2-group-outcomes-two.png)

저자들은 API 예산, 진료 예약, 개인 비서의 74개 시나리오를 MAMUBench(여러 사용자와 에이전트의 조정을 평가하는 벤치마크)로 공개할 계획이라고 적었다.
병합 대기열 3개는 이 공개 계획에 포함되지 않는다.

## **4. API Key: Agents Sharing a Contested Resource**

연구자 4~16명이 한정된 야간 API 토큰 예산(모델이 생성하는 텍스트 단위의 한도)을 공유한다.
각 사용자는 자기 작업의 마감과 중요도를 에이전트에게 알려 준다.
에이전트는 MCP\* 도구로 작업을 조회하거나 실행 규모를 바꾸고 취소할 수 있다.
평가는 마감까지 완료한 작업의 가치를 예산과 처리량 한도를 지킨 최적 계획의 가치로 나눠서 한다.

Opus 5에서 조정자는 최적 가치의 64%, 메시지 팀은 30%, 무통신 팀은 7%를 달성했다.
Sonnet 5에서는 각각 32%, 12%, 2%였다.
Opus 5의 집계에서는 API 오류로 메시지 팀을 끝까지 실행한 사례가 없었던 세 시나리오를 제외했다.

Sonnet 5 메시지 팀에서 작업에 한 번이라도 손댄 에이전트의 비율은 4명일 때 66%, 16명일 때 10%였다.
GPT-5.6-sol은 82%에서 25%로 떨어졌다.
실행 기록을 회귀분석으로 비교했을 때, 시작이 늦거나 끝내지 못한 작업에 토큰을 많이 쓴 실행에서 점수가 낮은 경향이 나타났다.
팀 규모별로 시나리오가 달라서 인원수만 늘렸을 때의 인과 효과로 볼 수는 없다.

![API 예산 실험에서 실제로 행동한 팀원 비율과 최적 가치 대비 점수 (논문 Figure 3)](https://momozzing.github.io/assets/images/worse-together/fig3-larger-api-key.png)

동료의 동의나 통보 없이 작업을 중단한 횟수도 따로 셌다.
GPT·Qwen 팀은 실행당 평균 3.9~7.1회, Sonnet 5는 0.59회, Opus 5는 0회였다.
네 명이 참여한 시나리오에서는 Jain 지수(사용자별 성과가 얼마나 고른지 나타내는 지표)로 성과 분포도 비교했다.
Opus 5는 Sonnet 5와 GPT 계열에 비해 성과를 더 고르게 나눴다.

저자들은 자기 작업 없이 전체 예산을 맡는 리더를 추가했다.
리더에게만 변경 권한을 주는 경우와, 팀원에게 변경 권한을 남겨 두고 리더는 조언하는 경우를 비교했다.
두 구성에서 자원 단위당 가치로 우선순위를 정하라는 지시를 주자, 사용자 4명과 8명 시나리오에서 조정자 점수를 넘었다.
16명 조건에서는 조정자 수준에 도달하지 못했다.
조정자에게는 같은 우선순위 지시를 주지 않았으므로 이 비교에는 역할과 지시의 차이가 함께 들어 있다.

병합 대기열에서는 사용자 네 명이 서로 다른 PR(코드 변경 요청)을 릴리스 마감 전에 머지하려 한다.
공유 CI(자동 빌드·테스트) 실행기는 한두 대다.
메시지 팀은 PR 댓글로 조정했다.
최적 계획 대비 병합 가치는 Opus 5에서 메시지 팀 81%, 조정자 92%였다.
Sonnet 5에서는 각각 78%, 93%였다.
우선순위를 모두에게 주고 리더가 마지막 순위의 PR을 이번 릴리스에서 빼도록 하자 두 모델 모두 평균 97%를 달성했다.

아래 표는 실행기 수와 CI 소요 시간이 다른 세 시나리오의 병합 가치를 보여 준다.
실행기가 하나인 조건에서 우선순위만 알려 준 Opus 5 팀은 97%, 거기에 마지막 PR을 빼는 지시도 받은 Sonnet 5 팀은 95%였다.
이 우선순위 실험은 시나리오당 실행 횟수가 대체로 5회였다.

## **5. Clinic: Urgent Scheduling and Displaced Patients**

이미 꽉 찬 진료 일정에 긴급 환자를 예약하려면 일반 환자의 시간을 옮겨야 한다.
긴급 환자를 기한 안에 예약하고 자리를 내준 환자도 다시 예약해야 성공이다.
팀에는 환자별 에이전트 17~52개가 있고 달력과 환자 노트를 공유한다.
긴급성을 판단할 정보가 한 통화에 모인 경우와 2~5통에 나뉜 경우를 비교했다.

정보가 흩어진 조건에서 GPT-5.6-sol 메시지 팀의 공동 성공률은 56.9%, 조정자는 92.6%였다.
정보가 한 통화에 모이면 각각 92.8%, 96.8%였다.
한편 두 팀이 모두 실행한 사례를 비교하면, Opus 5 무통신 팀은 81.0%, 메시지 팀은 69.5%였다.
공유 노트와 달력이 남아 있는 조건이므로 이 수치로 모든 정보 공유를 제거했을 때의 효과를 읽을 수는 없다.

![정보가 모인 경우와 흩어진 경우의 공동 성공률 및 누락 환자 분석 (논문 Figure 7)](https://momozzing.github.io/assets/images/worse-together/fig7-clinic-left-scenario-averaged.png)

정보가 흩어진 조건에서 Opus 5 메시지 팀이 놓친 환자 가운데 57.1%는 마지막 조작 시점에 담당 에이전트가 필요한 사실을 모두 갖고 있었다.
Sonnet 5는 같은 비율이 37.7%였다.
두 모델에서 정보가 담당자까지 도달하는 문제와, 알고도 예약을 끝내지 못하는 문제가 다른 비중으로 나타났다.

저자들은 당일 예약 기준을 구체화하고, 제삼자가 알려 준 정보에도 행동하며, 통화를 끝내기 전에 예약하라는 지시를 묶었다.
24개 시나리오에서 Opus 5 메시지 팀의 공동 성공률은 70.5%에서 95.3%로 올랐다.
같은 비교에 사용한 조정자 결과는 84.3%였다.
Sonnet 5의 메시지 팀은 65.3%에서 91.8%로 올랐고, 조정자는 74.2%였다.

## **6. Personal Assistant**

사용자 4명, 8명 또는 16명이 한 장바구니나 예약을 함께 쓴다.
예산이나 인원별 분담금 때문에 한 사람의 변경이 다른 사람의 선택에도 영향을 준다.
25개 시나리오마다 특정 사용자의 요청 한 가지를 정해 두고, 최종 주문이나 예약에 반영됐는지 확인했다.
주문이나 예약이 확정되지 않은 실행도 요청 미충족으로 집계한다.

Opus 5의 전체 요청 충족률은 조정자 88%, 메시지 팀 44%, 무통신 팀 6%였다.
Sonnet 5에서는 각각 75%, 37%, 4%였다.
주문이나 예약이 확정된 메시지 팀 실행에서 요청이 확정 담당자에게 전송된 비율은 모델별로 94~99%였다.
확정 시점에 그 요청이 담당자의 컨텍스트에 들어 있었던 비율은 47~67%였다.
요청이 컨텍스트에 있을 때 충족률은 56~68%, 없을 때는 19~36%였다.

다른 에이전트가 요청을 어기는 방향으로 장바구니나 예약을 수정한 경우도 흔했다.
네 모델에서 그런 수정이 한 번 이상 나온 실행은 약 65~77%였다.
사용자의 선호나 제약에 대해 근거 없는 말을 한 사례는 Claude 두 모델에서 따로 분류했다.
이 행동들이 전체 점수 차이를 일으켰는지는 실험에서 확인하지 못했다.

아래 그림의 왼쪽은 전체 시나리오와 안전 관련 요청이 있는 9개 시나리오의 충족률이다.
오른쪽은 이전에 실패했던 메시지 팀 실행을 같은 시작 상태에서 다시 돌렸을 때의 회복률이다.

![개인 비서의 요청 충족률과 실패 실행을 다시 돌린 뒤의 회복률 (논문 Figure 8)](https://momozzing.github.io/assets/images/worse-together/fig8-personal-assistant-left.png)

확정 담당자의 미확인 DM(에이전트 간 직접 메시지)이 남아 있으면 도구가 확정을 거절하게 했다.
Opus 5에서는 기본 재실행 45.5%에 비해 이 제약을 걸었을 때 73.1%가 회복됐다.
Sonnet 5에서는 30.3%에서 62.3%로 올랐다.
확정 권한만 리더에게 지정한 경우는 두 모델 모두 기본 재실행과 비슷했다.
회복률은 이전에 실패했고 재실행 분석 조건을 충족한 사례에 해당한다.
전체 요청 충족률과 분모가 다르다.

## **7. Implications for Safety**

사용자별 에이전트는 자기 사용자에게 맞는 행동을 하면서도 공유 자원에서 서로의 일을 방해할 수 있다.
개인 비서 실험에서는 안전 관련 요청을 다룬 9개 시나리오에서도 조정자가 메시지 팀보다 요청을 더 잘 지켰다.
여러 서비스에서 독립적으로 올라온 에이전트에는 실험처럼 공통 리더나 절차를 추가하기 어려울 수 있다.

## **8. Limitations**

MAMUBench의 74개 시나리오를 Opus 5 메시지 팀으로 한 번씩 돌리면 논문 추산 약 34억 토큰을 처리한다.
같은 모델로 해당 구성들을 모두 직렬 실행하면 약 370시간과 54억 토큰이 든다.
이 값은 전체 실행 규모를 보여 준다.
구성별 성능을 비교할 때는 같은 추론 비용을 부여하는 조건도 따로 시험할 만하다.

팀이 잘했는지는 환경 로그에서 자동 채점했다.
작업 중단의 동의 여부와 근거 없는 주장에는 Claude 판정기를 따로 썼고, 사람의 판정과 일치하는지는 검증하지 않았다.
환경마다 모델 범위, 추론 설정, 스케줄링, 통신 도구가 달랐다.
병합 대기열은 시나리오가 세 개뿐이고, 클리닉은 시뮬레이션이다.
특정 환경에서 효과가 난 지시나 확정 조건을 다른 환경에도 그대로 적용할 근거는 더 필요하다.

## **9. Conclusion**

네 환경에서 기본 메시지 팀은 평균적으로 단일 조정자보다 낮은 성과를 냈다.
API 예산에서는 참여가 줄고 완료하지 못한 일에 자원을 썼다.
개인 비서에서는 전송된 요청이 확정 전에 읽히지 않는 경우가 많았다.
환경에 맞춰 우선순위를 명시하거나 도구의 확정 조건을 바꾸자 일부 차이를 줄일 수 있었다.
